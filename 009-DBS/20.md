### **1. The Basics: What is a Transaction?**

A **transaction** is an executing program that forms a logical unit of database processing. It is a sequence of operations (reading, inserting, updating, or deleting data) that must be executed completely or not at all.

Think of a transaction like transferring money online. If you transfer $50 from your Checking account to your Savings account, the database must do two things:

1. Deduct $50 from Checking.
2. Add $50 to Savings.

If the system crashes after step 1, you lose $50. A transaction ensures that both steps succeed (**Commit**) or both steps fail and reverse (**Abort/Rollback**).

**Key Concepts:**

* **Multiuser DBMS:** Systems (like airline reservations or Amazon) where thousands of users access the database concurrently.
* **Interleaving:** The operating system doesn't execute one user's transaction entirely and then move to the next. It juggles them, executing a step from Transaction A, a step from Transaction B, and so on. This is where concurrency problems happen.

---

### **2. Concurrency Problems (When Transactions Collide)**

When multiple transactions are interleaved, they can step on each other's toes. Here are the five major problems that can occur, complete with formal definitions, intuitive explanations, and swimlane charts.

#### **A. The Lost Update Problem**

**Exam-Style Definition:** A concurrency anomaly that occurs when two or more transactions read the same data item, modify it, and write it back to the database, resulting in the later transaction overwriting and permanently erasing the updates made by the earlier transaction.

**Intuitive Explanation:** Two ticket agents (Agent A and Agent B) are trying to book the very last seat on Flight 101 at the exact same time.

| Time | Agent A (Transaction 1) | Agent B (Transaction 2) | Database State (Seats Left) |
| --- | --- | --- | --- |
| 1 | Reads available seats (Value = 1) |  | Seats = 1 |
| 2 |  | Reads available seats (Value = 1) | Seats = 1 |
| 3 | Books seat (1 - 1 = 0) |  | Seats = 1 |
| 4 | Writes new value: Seats = 0 |  | Seats = 0 |
| 5 |  | Books seat (1 - 1 = 0) | Seats = 0 |
| 6 |  | Writes new value: Seats = 0 | **Seats = 0 (Double Booked!)** |

> **The Result:** Both agents successfully booked a ticket, but the database only subtracted one seat. The airline now has an angry customer without a physical seat. Agent A's update was "lost."

---

#### **B. The Dirty Read Problem (Temporary Update)**

**Exam-Style Definition:** A concurrency problem where a transaction reads a database item that has been updated by another uncommitted transaction. If the uncommitted transaction fails and rolls back, the first transaction is left operating on invalid or "dirty" data that officially never existed in the database.

**Intuitive Explanation:** An e-commerce warehouse system is checking stock while a customer's credit card is being processed.

| Time | Customer Purchase (Transaction 1) | Inventory System (Transaction 2) | Database State (Laptops) |
| --- | --- | --- | --- |
| 1 | Reads laptops in stock (Value = 5) |  | Laptops = 5 |
| 2 | Deducts 1 laptop for cart (Value = 4) |  | Laptops = 5 |
| 3 | Writes temporary value: Laptops = 4 |  | **Laptops = 4 (Uncommitted)** |
| 4 |  | Reads laptops in stock (Value = 4) | Laptops = 4 |
| 5 | **Credit Card Declined!** |  | Laptops = 4 |
| 6 | Rolls back transaction (Restores to 5) |  | Laptops = 5 |
| 7 |  | Uses value '4' to reorder stock | **System makes wrong decision** |

> **The Result:** The inventory system ordered more laptops because it read a "4", but that 4 was a mirage. It was dirty data from a failed transaction.

---

#### **C. The Incorrect Summary Problem**

**Exam-Style Definition:** A concurrency issue where one transaction calculates an aggregate function over a set of records while another transaction is actively updating those same records. The aggregate function reads a mix of pre-update and post-update values, producing an inaccurate total.

**Intuitive Explanation:** A bank manager is running an end-of-day total of all funds, while a customer is actively transferring money from their Checking to their Savings.

| Time | Customer Transfer (Transaction 1) | Bank Manager Total (Transaction 3) | Database State |
| --- | --- | --- | --- |
| 1 | Reads Checking (Value = $100) |  | Checking=$100, Savings=$100 |
| 2 | Deducts $50 (Checking = $50) |  | Checking=$100, Savings=$100 |
| 3 | Writes Checking = $50 |  | Checking=$50, Savings=$100 |
| 4 |  | Reads Checking (Reads $50) | Checking=$50, Savings=$100 |
| 5 |  | Reads Savings (Reads $100) | Checking=$50, Savings=$100 |
| 6 |  | Calculates Total ($50 + $100 = $150) | Checking=$50, Savings=$100 |
| 7 | Reads Savings (Value = $100) |  | Checking=$50, Savings=$100 |
| 8 | Adds $50 to Savings (Value = $150) |  | Checking=$50, Savings=$100 |
| 9 | Writes Savings = $150 |  | Checking=$50, Savings=$150 |

> **The Result:** The bank manager's total says the bank holds $150, but the actual total across both accounts is $200. The money was "in transit" when the summary was calculated.

---

#### **D. The Unrepeatable Read Problem**

**Exam-Style Definition:** A concurrency anomaly where a single transaction reads the exact same piece of data multiple times, but retrieves different values each time because another transaction successfully modified and committed changes to that data between the reads.

**Intuitive Explanation:** You might wonder why a program would read the same data twice. Think of a checkout process:

* **Read 1:** A user searches for concert tickets. The database reads that there are 5 VIP tickets left. The user spends 3 minutes entering their credit card details.
* **Read 2:** When they click "Pay Now," the system *cannot* just assume those 5 tickets are still there. It must read the database a second time to verify the inventory. If someone else bought the tickets during those 3 minutes, Read 2 will yield a different value.

| Time | User Checkout (Transaction 1) | Another Buyer (Transaction 2) | Database State (VIP Tickets) |
| --- | --- | --- | --- |
| 1 | Reads available tickets (Value = 5) |  | Tickets = 5 |
| 2 | *Waits for user to type credit card* |  | Tickets = 5 |
| 3 |  | Reads available tickets (Value = 5) | Tickets = 5 |
| 4 |  | Buys 2 tickets, Writes value = 3 | Tickets = 3 |
| 5 | Reads available tickets again |  | Tickets = 3 |
| 6 | **Fails: Value changed from 5 to 3** |  | Tickets = 3 |

---

#### **E. The Phantom Read Problem**

**Exam-Style Definition:** A concurrency problem where a transaction executes a query returning a set of rows, but when the same query is repeated later within the same transaction, new rows have appeared or existing ones have disappeared due to another transaction inserting or deleting records in the meantime.

**Intuitive Explanation:** Generating an HR report of all employees in the "Sales" department.

| Time | HR Report (Transaction 1) | Hiring Manager (Transaction 2) | Database State |
| --- | --- | --- | --- |
| 1 | Queries all Sales staff (Finds 10 people) |  | 10 Sales Employees |
| 2 |  | Inserts new hire into Sales dept | 11 Sales Employees |
| 3 |  | Commits insertion | 11 Sales Employees |
| 4 | Re-runs query to get their salaries | **Finds 11 people!** | 11 Sales Employees |

> **Key Difference from Unrepeatable Read:** An *Unrepeatable Read* means the data inside a specific, existing row changed. A *Phantom Read* means the actual number of rows matching your search criteria changed.

---

### **3. Why Recovery is Needed**

Because of the chaos shown above (and hardware limitations), a Database Management System (DBMS) relies heavily on a **Recovery Subsystem**.

Transactions have two final states:

* **Committed:** All steps finished flawlessly. The changes are permanently recorded in the database.
* **Aborted:** Something went wrong, and the transaction has no effect on the database.

**Why transactions fail and require recovery:**

* **System Crashes:** The power goes out or the server restarts while a transaction is halfway done.
* **Transaction Errors:** A user tries to withdraw money they don't have, triggering an exception.
* **Concurrency Control Enforcement:** The database intentionally kills (aborts) a transaction to prevent a Lost Update or Deadlock.
* **Disk Failures:** Physical damage to the storage drives.

The recovery system keeps a constant log of every change. If a transaction aborts halfway through, the database uses this log to perfectly reverse (undo) every step, ensuring the database is always in a mathematically valid state.

### **5. Transaction Lifecycle and The System Log**

To keep track of what transactions are doing (and to reverse them if they fail), the database relies on specific state-change operations and a highly secure ledger called the System Log.

**Exam-Style Definition: Transaction Operations**
The core commands used by a Database Management System (DBMS) to manage the lifecycle of a transaction. These include `BEGIN` (starts the transaction), `READ/WRITE` (data access), `END` (signals no more operations), `COMMIT` (permanently applies changes), and `ROLLBACK/ABORT` (cancels and undoes all changes).

**Exam-Style Definition: The System Log**
An append-only, sequential file stored on a secure disk that acts as a continuous diary of all transaction activities. It records every time a transaction starts, alters a value (keeping both the `old_value` and `new_value`), commits, or aborts.

**Intuitive Explanation & Example:**
Think of the **System Log** like an airplane's "Black Box." No matter what happens to the airplane (the system), the black box records every single move.
Because writing directly to a hard drive is slow, the database writes these diary entries into a temporary "Log Buffer" in fast RAM first.

* **The Commit Point:** A transaction reaches its "commit point" only when all its changes have been successfully written into the log, and that log buffer is **force-written** (pushed from temporary RAM to the permanent disk). Once that log is physically on the disk, the transaction is officially safe. If the power goes out one second later, the database can use the log on the disk to rebuild exactly what happened.

### **6. DBMS-Specific Buffer Replacement Policies**

Main memory (RAM) is fast but limited. A database loads "pages" (blocks of data) from the slow disk into the fast RAM buffer to work on them. When the RAM buffer gets full, the database has to kick an old page out to make room for a new one. How does it choose who gets kicked out?

**Exam-Style Definition: Buffer Replacement Policies**
Algorithms used by the DBMS to determine which data pages should be evicted from the limited main memory cache when new pages need to be loaded from disk, optimizing to reduce slow disk I/O operations.

#### **A. Domain Separation (DS) Method**

* **Definition:** A policy that divides the buffer pool into distinct, dedicated regions (domains) for different types of data (e.g., indexes, data pages, log pages), managing each region independently.
* **Intuitive Explanation:** Imagine organizing your physical work desk. Instead of mixing everything in one pile, you tape off sections: one square for "Textbooks," one for "Scratch Paper," and one for "Exams." If your Textbook section gets full, you put a textbook away. You *never* throw away an Exam to make room for a Textbook. This prevents one massive query from kicking out all your important index pages.

#### **B. Hot Set Method**

* **Definition:** A policy that identifies and retains a specific set of highly accessed disk pages in memory until their associated query or operation is completely finished.
* **Intuitive Explanation:** Think of cooking a complex meal. Your "hot set" is your salt, pepper, and favorite spatula. Even if your kitchen counter gets crowded, you *do not* put the salt back in the pantry until the entire dinner is cooked, because you know you will reach for it repeatedly.

#### **C. DBMIN Method (Database Minimum)**

* **Definition:** An advanced policy that calculates a "locality set" (the exact minimum number of pages a specific query will repeatedly use) and allocates exactly that many buffers to the query based on its access pattern.
* **Intuitive Explanation:** Think of assigning company cars based on job requirements. A salesperson driving across the state (Nested Loop Join) gets a reliable sedan (multiple buffer pages), while an office worker who just needs to drop off mail once a day (Sequential Scan) gets a shared bicycle (1-2 pages). It gives every query *exactly* what it needs to be efficient, but no more.

### **7. The ACID Properties (The Golden Rules of Transactions)**

For a database to be considered reliable, its transactions must guarantee four fundamental properties, famously known as the ACID properties.

**Exam-Style Definition: ACID Properties**
A set of four systemic guarantees (Atomicity, Consistency, Isolation, Durability) enforced by the DBMS to ensure database transactions are processed reliably, even in the event of errors, power failures, or concurrent user overlap.

* **Atomicity (The "All or Nothing" Rule):**
* *Definition:* The guarantee that a transaction is an indivisible unit of work; either all of its operations succeed, or none of them do. (Handled by the Recovery subsystem).
* *Example:* When you buy a coffee with a debit card, the bank must deduct $5 from your account AND add $5 to the cafe's account. It cannot do just one.


* **Consistency (The "Rule Follower" Rule):**
* *Definition:* The requirement that any transaction will bring the database from one valid, consistent state to another, strictly adhering to all programmed rules and constraints.
* *Example:* If a bank has a rule that "An account balance cannot be negative," a transaction attempting to withdraw $100 from an account with $50 will be rejected to preserve consistency.


* **Isolation (The "Invisible" Rule):**
* *Definition:* The guarantee that concurrent execution of transactions leaves the database in the same state that would have been obtained if the transactions were executed sequentially. (Handled by Concurrency Control).
* *Example:* If two people try to buy the last concert ticket at the exact same time, the system isolates their actions so they don't see each other's temporary, half-finished math. One wins, one loses.


* **Durability (The "Carved in Stone" Rule):**
* *Definition:* The guarantee that once a transaction has been committed, its effects are permanently recorded in the system and will survive subsequent system crashes or power failures.
* *Example:* Once you receive the "Booking Confirmed" screen for a flight, that data is physically written to the hard drive. If the airline's server room loses power a millisecond later, your ticket is still there when they reboot.



---

### **8. Levels of Isolation (Value Addition)**

Isolation is expensive. Strict isolation slows down the database because transactions have to wait in line. Therefore, databases offer different "Levels" of isolation. The higher the level, the safer the data, but the slower the performance.

* **Level 0:** Ignores almost all rules. (Allows Dirty Reads).
* **Level 1:** Prevents Lost Updates. (Transactions don't overwrite each other).
* **Level 2:** Prevents Lost Updates AND Dirty Reads.
* **Level 3 (True Isolation):** Prevents Lost Updates, Dirty Reads, and Unrepeatable Reads.

**Snapshot Isolation (A modern approach):**
Instead of making transactions wait in line (locking data), the database takes a photograph (snapshot) of the entire database exactly when the transaction starts. The transaction does all its work looking at this photograph. This perfectly prevents the **Phantom Read** problem because even if someone else inserts a new row, it won't appear in the photograph taken 5 minutes ago.

### **10. Schedules and Conflicts**

When a database handles hundreds of users, it doesn't process one person's transaction completely and then move to the next. It juggles them. This juggling act is called a schedule.

**Exam-Style Definition: Schedule (or History)**
An execution sequence that represents the chronological order of operations (reads, writes, commits, aborts) from multiple concurrent transactions. While operations from different transactions can be interleaved, the operations *within* a single transaction must remain in their original sequence.

**Exam-Style Definition: Conflicting Operations**
Two operations in a schedule are said to conflict if they meet ALL three of these conditions:

1. They belong to different transactions.
2. They access the exact same data item (e.g., both touch account `X`).
3. At least one of the operations is a `WRITE` (modify).

**Intuitive Explanation:** Two `READ` operations never conflict because simply looking at data doesn't change it for anyone else. But the moment someone tries to `WRITE` (change) the data, order matters.

* **Read-Write Conflict:** T1 reads X, then T2 writes X. If we flip the order (T2 writes X, then T1 reads X), T1 gets a completely different number.
* **Write-Write Conflict:** T1 writes X=90, then T2 writes X=120. The final value is 120. If we flip the order, the final value is 90.

---

### **11. Serial vs. Serializable Schedules**

**Exam-Style Definition: Serial Schedule**
A schedule where transactions are executed consecutively, one completely after the other, with absolutely no interleaving of operations.

**Exam-Style Definition: Serializable Schedule**
A non-serial (interleaved) schedule that produces the exact same final database state as some theoretical serial execution. It gives the performance benefits of concurrent execution while maintaining the mathematical correctness of a serial schedule.

**Intuitive Explanation:** A **Serial Schedule** is like a single-lane drive-thru. Car A orders, pays, and leaves before Car B can even look at the menu. It is 100% safe, but incredibly slow.
A **Serializable Schedule** is like a busy restaurant kitchen. Five chefs are cooking different meals at the same time (interleaved), but they coordinate perfectly so the final plates look exactly as if they had cooked them one by one.

---

### **12. Characterizing Schedules Based on Recoverability**

When a transaction fails, the database must undo it. But because transactions are interleaved, undoing one transaction might ruin another. Databases classify schedules by how easy they are to recover.

#### **A. Nonrecoverable Schedule (The Disaster)**

**Exam-Style Definition:** A schedule where a transaction (T2) reads a value updated by an uncommitted transaction (T1), and T2 commits *before* T1 commits. If T1 subsequently aborts, T2 cannot be rolled back because it has already been permanently committed.

**Intuitive Explanation:** "T2 trusted T1, but T1 lied." T2 took dirty data, finalized it, and told the user it was successful. Now the database is permanently corrupted. **Databases strictly prohibit this.**

| Time | Transaction 1 (T1) | Transaction 2 (T2) | Note |
| --- | --- | --- | --- |
| 1 | `w1(X)`: Writes new value for X |  | *X is modified but not committed* |
| 2 |  | `r2(X)`: Reads T1's uncommitted X | *T2 reads dirty data* |
| 3 |  | `c2`: **Commits!** | *T2 finalizes its work* |
| 4 | `a1`: **Aborts!** |  | *T1 reverses its change to X.* |
| **Result** | *Successfully rolled back* | *Committed invalid data!* | **NONRECOVERABLE** |

#### **B. Recoverable Schedule**

**Exam-Style Definition:** A schedule where a transaction (T2) that reads data modified by another transaction (T1) waits to commit until *after* T1 has committed.

**Intuitive Explanation:** T2 can read T1's unfinished work, but the database forces T2 to wait at the "checkout counter" until T1 officially pays (commits). If T1 fails, T2 can still be aborted because it hasn't committed yet.

| Time | Transaction 1 (T1) | Transaction 2 (T2) | Note |
| --- | --- | --- | --- |
| 1 | `w1(X)`: Writes new value for X |  |  |
| 2 |  | `r2(X)`: Reads T1's uncommitted X |  |
| 3 | `c1`: **Commits!** |  | *T1 finalizes first* |
| 4 |  | `c2`: **Commits!** | *T2 is now safe to commit* |

#### **C. Cascading Rollback (The Domino Effect)**

**Exam-Style Definition:** A phenomenon in some recoverable schedules where the failure (abort) of a single transaction triggers the forced rollback of multiple other uncommitted transactions because they read its intermediate data.

**Intuitive Explanation:** T1 builds a foundation. T2 builds the first floor. T3 builds the roof. If T1 realizes the foundation is cracked and aborts, the database must destroy T2 and T3's work as well. It's recoverable, but wastes a massive amount of computing time.

| Time | Transaction 1 (T1) | Transaction 2 (T2) | Note |
| --- | --- | --- | --- |
| 1 | `w1(X)`: Writes new value for X |  |  |
| 2 |  | `r2(X)`: Reads uncommitted X |  |
| 3 |  | `w2(Y)`: Does some heavy work | *Wasting time based on X* |
| 4 | `a1`: **Aborts!** |  | *T1 fails* |
| 5 |  | `a2`: **Forced to Abort!** | *Cascading Domino Effect* |

#### **D. Cascadeless Schedule**

**Exam-Style Definition:** A schedule that guarantees cascading rollbacks will never occur by strictly enforcing that every transaction only reads data that has already been committed.

**Intuitive Explanation:** To stop the dominos from falling, we just stop transactions from reading dirty data. T2 is forced to wait until T1 completely finishes before it is allowed to even *look* at item X.

| Time | Transaction 1 (T1) | Transaction 2 (T2) | Note |
| --- | --- | --- | --- |
| 1 | `w1(X)`: Writes new value for X |  |  |
| 2 |  | *Wants to read X... WAITS* | *Prevented from dirty read* |
| 3 | `c1`: **Commits!** |  | *X is now permanent* |
| 4 |  | `r2(X)`: Finally reads X | *100% Safe, no dominos* |

#### **E. Strict Schedule (The Safest)**

**Exam-Style Definition:** The most restrictive schedule where a transaction can neither read *nor write* a data item until the last transaction that wrote to it has either committed or aborted.

**Intuitive Explanation & Difference from Cascadeless:** Cascadeless only stops you from *reading* uncommitted data. But what if T1 writes X=5, and before T1 commits, T2 writes X=8? If T1 aborts, the database's simple "undo" mechanism might mistakenly erase T2's valid "8" and restore the original value (say, 9).

A **Strict Schedule** prevents this entirely. T2 cannot read *or overwrite* T1's work until T1 is completely out of the picture. This makes the database's recovery math incredibly simple and foolproof.

### **13. Summary Table: Schedules and Recoverability**

Use this table to quickly distinguish the hierarchy of schedules. Remember: **Strict $\subset$ Cascadeless $\subset$ Recoverable**.

| Schedule Type | The Rule / Behavior | Consequence if T1 Aborts | Real-World Status |
| --- | --- | --- | --- |
| **Nonrecoverable** | T2 reads uncommitted data and commits before T1. | **Disaster.** T2 committed a lie and cannot be rolled back. | *Never allowed by a DBMS.* |
| **Recoverable** | T2 reads uncommitted data, but waits for T1 to commit first. | T2 must also be aborted. | *Allowed, but risky.* |
| **Cascading Rollback** | Not a schedule type, but a side-effect of basic Recoverable schedules. | Multiple innocent transactions must be destroyed and redone. | *A performance nightmare.* |
| **Cascadeless** | T2 is only allowed to **read** committed data. | T2 is unaffected. No dominos fall. | *Good, prevents wasted work.* |
| **Strict** | T2 can neither **read nor write** data until it is committed. | Simple "Undo" perfectly restores the data. | *The standard for most DBMS.* |

### **The Core Concepts: Serializability Defined**

**The Formal Definition:**
A schedule $S$ is **conflict serializable** if it is conflict-equivalent to some serial schedule $S'$. Two schedules are conflict-equivalent if the relative order of any two conflicting operations is identical in both schedules.

**The "Easy English" Definition:**
Imagine two chefs (Transactions) sharing one kitchen (the Database).

* **Serial:** Chef 1 cooks their entire meal, cleans up, and leaves. Then, Chef 2 cooks their entire meal. (Safe, but extremely slow).
* **Serializable:** Both chefs are in the kitchen at the same time, chopping and boiling simultaneously. However, their timing is so perfectly coordinated that the final dishes taste *exactly* as if they had cooked completely one after the other. (Fast and safe).

---

### **Comparing Schedule Types**

| Schedule Type | Description | Concurrency | Correctness |
| --- | --- | --- | --- |
| **Serial** | Transactions execute completely one after another with zero overlapping. | None (wastes CPU time waiting for I/O). | 100% Guaranteed. |
| **Serializable** | Operations interleave, but the outcome and data state match a serial execution. | High. | 100% Guaranteed. |
| **Nonserializable** | Operations interleave randomly, causing data conflicts and corruption. | High. | Fails completely. |

### **Detailed Breakdown: Algorithm 20.1 (Testing for Serializability)**

You specifically asked for clarity on the testing algorithm. Textbooks call this building a **Precedence Graph** or **Serialization Graph**.

The goal of this algorithm is simple: **We need to see if two transactions are stepping on each other's toes in a loop.** Here is the step-by-step, plain-English breakdown.

**Step 1: Identify the Nodes (The Actors)**
Every transaction (e.g., $T_1$, $T_2$, $T_3$) gets its own circle (node) drawn on a piece of paper.

**Step 2: Understand What a "Conflict" Is**
A conflict *only* happens when three strict rules are met simultaneously:

1. They belong to **different** transactions.
2. They are trying to access the **exact same piece of data** (e.g., Bank Account A).
3. At least one of them is **writing** (changing the data). Two separate transactions just reading data will never conflict.

**Step 3: Draw the Arrows (The Edges)**
Look at the timeline of events. If a conflict occurs, draw a one-way arrow from the transaction that acted *first* to the transaction that acted *second*. There are only three scenarios that trigger an arrow:

* **Read-Write Conflict:** $T_1$ reads a value, and later $T_2$ overwrites it. Draw an arrow: $T_1 \rightarrow T_2$.
* **Write-Read Conflict:** $T_1$ writes a value, and later $T_2$ reads that newly written value. Draw an arrow: $T_1 \rightarrow T_2$.
* **Write-Write Conflict:** $T_1$ writes a value, and later $T_2$ overwrites it again. Draw an arrow: $T_1 \rightarrow T_2$.

**Step 4: Check for Cycles (The Verdict)**
Look at your drawing. Trace the arrows with your finger.

* Can you follow the arrows and end up back at the exact circle you started from? If **YES**, you have a cycle. The schedule is **NOT serializable**. Data corruption will occur.
* Are all arrows pointing forward with no loops? If **NO CYCLE** exists, the schedule is **serializable**. It is safe to execute!

---

### **Why "Result Equivalence" is Dangerous**

Your notes mention that comparing the final database state (Result Equivalence) is a bad way to test schedules.

Imagine $X = 100$.

* Schedule 1: $T_1$ adds 50. $T_2$ subtracts 50. Final $X = 100$.
* Schedule 2: $T_1$ multiplies by 1. $T_2$ does nothing. Final $X = 100$.

Both schedules resulted in 100, but they did entirely different math and executed entirely different logic. It was purely an accident that the final numbers matched. We must track *conflicting operations* (Conflict Equivalence), not just the final number.

### **Real-World System Examples**

In the real world, database systems (DBMS) like PostgreSQL, MySQL, or Oracle **do not actually use Algorithm 20.1 in real-time.** Why? Because constantly drawing graphs and checking for cycles for thousands of transactions per second would crash the system. Instead, they use **Protocols** (strict rules) that guarantee a cycle can never form in the first place.

* **E-Commerce Inventory (Using Two-Phase Locking):** When you try to buy the last pair of sneakers on Amazon, the database places an exclusive "Write Lock" on that inventory number. If someone else tries to buy it, their transaction must wait until yours is finished. The protocol forces a serializable outcome without needing a graph.
* **Banking Systems (Using Timestamp Ordering):** If you transfer funds from Savings to Checking, the database assigns a unique timestamp to your transaction. If an older transaction tries to overwrite a balance that a newer transaction already updated, the DBMS immediately aborts the older one and restarts it, preventing any cycles.
