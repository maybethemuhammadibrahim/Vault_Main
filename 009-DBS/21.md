## 21.1 Two-Phase Locking Techniques for Concurrency Control

### 1. The Concept of a Lock

> **Formal Definition:** A lock is a variable associated with a data item describing the status for operations that can be applied. There is one lock for each item in the database.

Locks are used to enforce mutual exclusion and ensure that multiple transactions ($T_1$, $T_2$, etc.) do not interfere with each other when accessing the same data.

### 2. Binary Locks

> **Formal Definition:** A binary lock can have two states or values: locked and unlocked (or 1 and 0, for simplicity). A distinct lock is associated with each database item $X$.

**Intuitive Explanation:** Think of a binary lock as a simple "occupied/vacant" sign on a restroom door. If it is vacant (0), a transaction can enter, lock the door (change to 1), and use the item. If it is occupied (1), any other transaction must wait outside until the door is unlocked.

**Rules for Binary Locks:**

1. A transaction $T$ must issue `lock_item(X)` before any `read_item(X)` or `write_item(X)`.
2. $T$ must issue `unlock_item(X)` after all read/write operations are completed.
3. $T$ will not issue `lock_item(X)` if it already holds the lock.
4. $T$ will not issue `unlock_item(X)` unless it already holds the lock.

### 3. Shared/Exclusive (Read/Write) Locks

Binary locks are too restrictive. If $T_1$ and $T_2$ only want to *read* item $X$, they don't actually conflict. Forcing them to wait for each other slows down the system.

To fix this, we use a multiple-mode lock with three states: **read-locked**, **write-locked**, or **unlocked**.

* **Read-locked (Shared lock):** Other transactions are allowed to read the item simultaneously.
* **Write-locked (Exclusive lock):** A single transaction exclusively holds the lock. No other transaction can read or write to it.

> **Answers to your questions regarding Read/Write Locks:**
> **1. In case of a write lock, can the transaction both read and write?**
> Yes. If a transaction holds a write (exclusive) lock on item $X$, it has complete monopoly over that item. It is perfectly allowed to both `read_item(X)` and `write_item(X)`.
> **2. In case of a read lock, can the transaction only read?**
> Yes. If a transaction *only* holds a read (shared) lock on item $X$, it is restricted to `read_item(X)`. If it wants to write to $X$, it must first upgrade its lock to a write lock (assuming no other transactions are currently sharing the read lock).

#### Pseudocode for Read/Write Lock Operations

Below is the formal logic for how the Lock Manager handles requests.

```pascal
read_lock(X):
    B: if LOCK(X) = "unlocked"
        then begin 
            LOCK(X) ← "read-locked";
            no_of_reads(X) ← 1
        end
    else if LOCK(X) = "read-locked"
        then no_of_reads(X) ← no_of_reads(X) + 1
    else begin
        wait (until LOCK(X) = "unlocked" and the lock manager wakes up the transaction);
        go to B
    end;

write_lock(X):
    B: if LOCK(X) = "unlocked"
        then LOCK(X) ← "write-locked"
    else begin
        wait (until LOCK(X) = "unlocked" and the lock manager wakes up the transaction);
        go to B
    end;

unlock(X):
    if LOCK(X) = "write-locked"
        then begin 
            LOCK(X) ← "unlocked";
            wakeup one of the waiting transactions, if any
        end
    else if LOCK(X) = "read-locked"
        then begin
            no_of_reads(X) ← no_of_reads(X) - 1;
            if no_of_reads(X) = 0
                then begin 
                    LOCK(X) = "unlocked";
                    wakeup one of the waiting transactions, if any
                end
        end;

```

**Lock Conversion:**

* **Upgrading:** Changing a read lock to a write lock (must wait if others are also reading).
* **Downgrading:** Changing a write lock to a read lock.

### 4. Guaranteeing Serializability by Two-Phase Locking (2PL)

> **Formal Definition:** A transaction is said to follow the two-phase locking protocol if all locking operations (`read_lock`, `write_lock`) precede the first `unlock` operation in the transaction.

A 2PL transaction is strictly divided into two phases:

1. **Expanding (Growing) Phase:** New locks can be acquired, but none can be released. Upgrades happen here.
2. **Shrinking Phase:** Existing locks can be released, but *no new locks can be acquired*. Downgrades happen here.

### 5. Intuitive Explanation: How 2PL Limits Concurrency

*You asked for a clearer explanation of the paragraph stating: "Two-phase locking may limit the amount of concurrency that can occur..."*

**The Explanation:**
Think of 2PL as a strict hoarder's rule: *Once you start throwing things away (unlocking), you can never bring anything new into the house (locking).* Because of this rule, a transaction might finish using an item (let's say item $X$) very early on. Logically, it should just return $X$ so others can use it. However, if the transaction knows it will need item $Y$ later, the 2PL rule strictly forbids it from releasing $X$ right now. It must hold onto $X$ (like a hostage) until it successfully grabs the lock for $Y$.

As a result, other transactions that only need $X$ are stuck waiting in line, even though $X$ is sitting idle. This forced waiting reduces **concurrency** (the amount of parallel work the database can do). It is the price we pay: we sacrifice some speed and efficiency to completely guarantee **serializability** (mathematical safety).

---

### 6. Variations of Two-Phase Locking

1. **Basic 2PL:** The standard expanding/shrinking phases described above.
2. **Conservative (Static) 2PL:** A transaction must lock *all* items it will ever need before it even begins execution. If it can't get all of them, it gets none and waits. **Pro:** Completely deadlock-free. **Con:** Very hard to use in practice because transactions rarely know exactly what they need before they run.

> **Answer to your question regarding Strict vs. Rigorous 2PL:**
> **3. I do not clearly understand the difference between strict 2PL and rigorous, one locks the write lock and the other locks both, aren't they the same?**
> They are not the same; the difference lies strictly in **what types of locks are held until the very end** of the transaction.
> * **Strict 2PL:** A transaction does not release any **Exclusive (Write) locks** until it commits or aborts. However, it *is* allowed to release Shared (Read) locks earlier (during the shrinking phase). This is the most popular variation because it prevents "cascading rollbacks" (where one failing transaction forces others to fail because they read uncommitted data).
> * **Rigorous 2PL:** A transaction does not release **ANY locks (neither Read nor Write)** until it commits or aborts.
> 
> 
> **In short:** Strict 2PL lets go of Read locks early but holds Write locks to the end. Rigorous 2PL holds absolutely everything (Read and Write) until the very end. Rigorous is easier to implement but limits concurrency even more than Strict 2PL.

## 21.1.3 Deadlock Concepts & Prevention

### 1. The Concept of Deadlock

> **Formal Definition:** Deadlock occurs when each transaction $T$ in a set of two or more transactions is waiting for some item that is locked by some other transaction $T'$ in the set.

**Intuitive Explanation:** It is a Mexican standoff. $T_1$ has item X and needs item Y. $T_2$ has item Y and needs item X. Both are stuck in a waiting queue forever because neither will release their lock until they get what the other one has.

### 2. Deadlock Prevention Protocols

These are strict rules designed to ensure a deadlock state can *never* mathematically occur, though they usually limit concurrency (parallel processing).

* **Conservative 2PL:** A transaction must lock *all* items it needs in advance. If it fails to get even one, it drops everything and waits to try again. (Highly impractical).
* **Item Ordering:** All database items are given a strict global order. A transaction must request locks following this exact sequence. (Impractical for programmers).

## 21.1.4 Deadlock Prevention using Timestamps

> **Formal Definition:** A transaction timestamp $TS(T)$ is a unique identifier assigned to each transaction based on the order in which they are started.

* If $T_1$ starts before $T_2$, then $TS(T_1) < TS(T_2)$.
* **Crucial Rule:** The *older* transaction has the *smaller* timestamp value.

### Wait-Die vs. Wound-Wait Schemes

Suppose transaction $T_i$ tries to lock an item $X$ that is currently locked by $T_j$.

* **Wait-Die:** * If $TS(T_i) < TS(T_j)$ ($T_i$ is older), $T_i$ is allowed to **wait**.
* If $TS(T_i) > TS(T_j)$ ($T_i$ is younger), $T_i$ **dies** (aborts and restarts with the same timestamp).


* **Wound-Wait:**
* If $TS(T_i) < TS(T_j)$ ($T_i$ is older), $T_i$ **wounds** $T_j$ ($T_j$ is aborted).
* If $TS(T_i) > TS(T_j)$ ($T_i$ is younger), $T_i$ is allowed to **wait**.



> ### 💡 The Memory Trick for Wait-Die / Wound-Wait
> 
> 
> To stop these from getting jumbled, remember this single rule: **The name of the algorithm tells you exactly what happens based on the age of the requester ($T_i$).** >
> Always view the transaction requesting the lock ($T_i$) as the main character. The **Older** transaction is the "VIP", and the **Younger** transaction is the "Peasant". The VIP *never* gets aborted.
> * **WAIT-DIE:** >     * If the Requester is **Older** (VIP), it **WAITS**.
> * If the Requester is **Younger** (Peasant), it **DIES**.
> 
> 
> * **WOUND-WAIT:**
> * If the Requester is **Older** (VIP), it **WOUNDS** (kills the peasant holding the lock).
> * If the Requester is **Younger** (Peasant), it **WAITS**.
> 
> 
> 
> 

### Other Waiting Schemes

* **No Waiting:** If a transaction cannot get a lock, it immediately aborts and restarts after a delay. (Causes needless aborts).
* **Cautious Waiting:** If $T_i$ tries to lock an item held by $T_j$:
* If $T_j$ is *not blocked* (not waiting on anyone else), $T_i$ is allowed to wait.
* If $T_j$ *is blocked*, $T_i$ is aborted.
* *Why this works:* It creates a total ordering of blocking times ($b(T)$), making cycles (deadlocks) impossible.

## 21.1.5 Deadlock Detection & Timeouts

If we don't actively *prevent* deadlocks, we must occasionally check if one has happened and fix it.

* **Wait-For Graph:** The system draws a directed graph of executing transactions.
* A node is created for each transaction.
* A directed edge ($T_i \rightarrow T_j$) is created if $T_i$ is waiting for an item locked by $T_j$.
* **Rule:** We have a state of deadlock *if and only if* the wait-for graph has a cycle (a loop).


* **Timeouts:** If a transaction waits for a lock longer than a system-defined time limit, the system simply assumes it is deadlocked and aborts it. (Very simple, low overhead).

## 21.2 The Timestamp Ordering (TO) Algorithm

Unlike 2PL, Timestamp Ordering (TO) **does not use locks**. Instead, it forces transactions to execute in the exact equivalent serial order of their timestamps.

Every database item $X$ tracks two timestamps:

1. **$read\_TS(X)$:** The largest timestamp of any transaction that successfully *read* $X$. (The youngest transaction to read it).
2. **$write\_TS(X)$:** The largest timestamp of any transaction that successfully *wrote* $X$. (The youngest transaction to write it).

### Basic TO Rules

Whenever transaction $T$ wants to access item $X$, the algorithm checks if $T$'s timestamp violates chronological history. If $T$ is trying to interact with an item that a *younger* transaction has already messed with, $T$ is "out of time" and must be aborted/restarted.

**1. Write Check (When $T$ issues `write_item(X)`):**

* If $read\_TS(X) > TS(T)$ **OR** $write\_TS(X) > TS(T)$: Abort and rollback $T$. *(A younger transaction already read or wrote $X$ before $T$ got here).*
* Else: Execute the write and update $write\_TS(X)$ to $TS(T)$.

**2. Read Check (When $T$ issues `read_item(X)`):**

* If $write\_TS(X) > TS(T)$: Abort and rollback $T$. *(A younger transaction already overwrote the data $T$ was supposed to read).*
* Else: Execute the read and update $read\_TS(X)$ to the larger of $TS(T)$ and the current $read\_TS(X)$.

*Note: Basic TO can cause **cascading rollbacks** (if $T$ is aborted, any transaction that read $T$'s data must also be aborted).*

### Variations of Timestamp Ordering

* **Strict TO:** To prevent cascading rollbacks, if $T$ wants to read/write an item written by $T'$, and $TS(T) > write\_TS(X)$, $T$ is delayed until $T'$ commits or aborts. (Simulates locking without causing deadlocks).
* **Thomas's Write Rule:** Modifies the Basic TO Write Check to reject fewer operations.
* If $read\_TS(X) > TS(T)$: Abort $T$.
* If $write\_TS(X) > TS(T)$: **Do not execute the write, but DO NOT abort $T$.** Just continue. *(Since a younger transaction already wrote $X$, $T$'s write is obsolete anyway. We can just ignore it safely).*
* Else: Execute the write.
