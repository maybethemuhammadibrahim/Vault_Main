# Paging — Detailed Notes

---

## 1. The 90/10 Rule (Locality of Reference)

**Formal Definition:** Processes spend 90% of their execution time accessing only 10% of their address space in memory.

**Intuitive Explanation:** Imagine you have a 500-page textbook. During your study session, you keep flipping between the same 50 pages (your current chapter). You rarely touch the other 450 pages. Programs behave the same way — they loop over the same code and data repeatedly. This means we **don't need the entire program in memory** at once; just the "hot" 10% is enough most of the time.

**Mental Model:** Think of it like your desk. You have hundreds of files in your cabinet, but only a small stack is on your desk at any time — those are the ones you're actively working with.

---

## 2. What is Paging?

**Formal Definition:** Paging is a memory-management scheme that permits a process's physical address space to be **non-contiguous**. It breaks physical memory into fixed-sized blocks called **frames** and logical memory into blocks of the same size called **pages**.

**Key Properties:**
- Eliminates **external fragmentation** (no holes between allocations)
- May have some **internal fragmentation** (wasted space inside the last frame)
- Logical address space is completely separate from physical address space
- A process can have a 64-bit logical address space even if the system has far less physical RAM

**Intuitive Explanation:** Instead of trying to fit an entire program into one big contiguous chunk of RAM (like finding a parking lot big enough for your whole convoy), paging chops the program into equal-sized pieces (pages) and scatters them into any available equal-sized slots (frames) in physical memory. The page table keeps track of where each piece went.

---

## 3. Pages vs. Frames — The Core Distinction

### Your Question Answered

> *"Are pages and frames of equal sizes? Why two different names?"*

**Yes, pages and frames are always the same size.** The two different names exist because they live on two different sides:

| Aspect | Page | Frame |
|---|---|---|
| **Side** | Logical (virtual) memory | Physical (real) memory |
| **What it is** | A fixed-size block of the *program's* address space | A fixed-size slot in *physical RAM* |
| **Determined by** | The program's logical layout | The hardware's physical layout |
| **Analogy** | A page of your essay | A slot/pocket in a binder |

**Intuitive Explanation:** Think of it like a jigsaw puzzle:
- **Pages** = the individual puzzle pieces (your program chopped up)
- **Frames** = the slots on the puzzle board (physical RAM divided into equal compartments)

Each puzzle piece (page) fits into exactly one slot (frame), and they're the same size. We need two names because a "page" is the program's view, and a "frame" is RAM's view. **Page 0 of your program might sit in Frame 47 of RAM** — the page table records this mapping.

**Your understanding is correct:** Frames are predetermined fixed blocks in physical memory, and pages are the program broken into fixed-size blocks that get assigned to those frames.

## 4. Logical Address Breakdown

**Formal Definition:** Every address generated by the CPU is divided into two parts:
- **Page number (p):** Used as an index into the page table
- **Page offset (d):** The position within that page/frame

```
[ Page Number (p) | Page Offset (d) ]
```


If the logical address space is **2^m** and the page size is **2^n** bytes:
- **Page number** = high-order **(m − n)** bits
- **Page offset** = low-order **n** bits

### Calculation Explained

> **Why power of 2?** Because binary computers can split an address into page number and offset by simply taking the upper bits and lower bits — no division needed! It's a free operation in hardware.

**Example:** If m = 32 (32-bit address space) and n = 12 (4 KB pages = 2^12):
- Page number = upper 32 − 12 = **20 bits** → can address **2^20 = ~1 million pages**
- Page offset = lower **12 bits** → can address **4096 bytes within a page**

---

## 5. Address Translation (How MMU Converts Logical → Physical)

**Steps performed by the MMU:**

1. **Extract** the page number `p` from the logical address
2. **Look up** `p` in the page table → get frame number `f`
3. **Replace** `p` with `f` in the address; keep offset `d` unchanged
4. **Result:** Physical address = `f` concatenated with `d`

**Formula:** `Physical Address = Base address of frame f + page offset d`

**Mental Model:** It's like a mail forwarding system. Your letter says "Page 3, byte 500" (logical). The page table says "Page 3 lives in Frame 17." So the physical address becomes "Frame 17, byte 500." The offset (byte 500) never changes — it's the same position within the block regardless of which block it is.

## 6. Internal Fragmentation in Paging

**Formal Definition:** Since frames are allocated as whole units, if a process's memory requirements don't align with page boundaries, the last allocated frame may not be completely full. The unused portion is **internal fragmentation**.

**Expected average waste:** **1/2 page per process**

### Textbook Example

> Page size = **2,048 bytes**
> Process size = **72,766 bytes**
> Pages needed = 72,766 ÷ 2,048 = **35 full pages + 1,086 bytes remaining**
> Frames allocated = **36**
> Internal fragmentation = 2,048 − 1,086 = **962 bytes wasted**

### Worst Case

A process needs `n` pages + **1 byte** → allocated `n + 1` frames → wastes almost an entire frame (2,048 − 1 = 2,047 bytes).

### Trade-off: Page Size

| Smaller Pages | Larger Pages |
|---|---|
| Less internal fragmentation | More internal fragmentation |
| More page-table entries (overhead) | Fewer page-table entries |
| More disk I/O operations | More efficient disk I/O |

**Modern systems:** Typically **4 KB or 8 KB**. Some support multiple sizes:
- **x86-64 + Windows 10:** 4 KB and 2 MB
- **Linux:** Default ~4 KB + architecture-dependent **huge pages**

### Page Table Entry Size Calculation

> On a 32-bit CPU, each page-table entry is typically **4 bytes (32 bits)**.
> A 32-bit entry can point to one of **2^32 physical frames**.
> If frame size = 4 KB (2^12), then addressable physical memory = **2^32 × 2^12 = 2^44 bytes = 16 TB**.

**Key insight:** The size of physical memory a paged system can address is often **different from** the maximum logical address space size. Additional bits in each page-table entry (valid bit, protection bits, etc.) reduce the bits available for the frame number.

## 7. Frame Allocation at Process Creation

**Process:**
1. Process arrives; its size is measured in pages (needs `n` pages)
2. System checks for `n` free frames
3. Each page is loaded into an allocated frame
4. The frame number for each page is recorded in the process's page table

## 8. Two Views of Memory

| Programmer's View | Paging (OS) View |
|---|---|
| Memory is **one single contiguous space** | Program is **scattered** across physical memory, interleaved with other programs |
| Addresses go from 0 to max linearly | Pages mapped to arbitrary frames via page table |

## 9. Frame Table vs. Page Table

| Feature | Frame Table | Page Table |
|---|---|---|
| **Scope** | System-wide (one for entire OS) | Per-process (each process has its own) |
| **Indexed by** | Physical frame number | Logical page number |
| **Contains** | Whether frame is free or allocated; if allocated, which process/page owns it | Frame number corresponding to each logical page |

> **Interchangeable terms alert:** "Page table entry" and "PTE" mean the same thing.

---

## 10. Page Table and Context Switching

- The page table is used by the **CPU dispatcher** to configure hardware page tables when a process gets the CPU
- A **pointer to the page table** is stored in the **PCB (Process Control Block)** alongside other register values
- When the CPU scheduler selects a process, it must reload:
  - User registers
  - Hardware page-table values from the stored page table
- **Paging increases context-switch time** because of this extra reload work

---

## 11. Translation Look-Aside Buffer (TLB)

**Formal Definition:** The TLB is a **cache-like hardware component** (high-speed associative memory) that stores recently accessed **virtual-to-physical address translations**. It reduces the overhead of frequent page-table lookups.

> **Interchangeable terms:** TLB = "Translation Look-Aside Buffer" = "associative memory cache for page table" = "address-translation cache"

### How TLB Works

1. CPU generates a virtual address
2. **TLB is checked first:**
   - **TLB Hit** → physical address retrieved directly (fast, 1 memory access for the data)
   - **TLB Miss** → page table in memory is consulted (slow), translation is retrieved and **stored in TLB** for future use
3. Data is accessed using the physical address

### The Two-Memory-Access Problem

**Without TLB:** Every memory reference requires **2 memory accesses**:
1. One to read the page-table entry
2. One to read the actual data

This **doubles** memory access time — unacceptable!

**With TLB (on hit):** Only **1 memory access** (for the data itself; the translation comes from the fast TLB hardware).

### Address-Space Identifiers (ASIDs)

**Formal Definition:** ASIDs are identifiers stored in each TLB entry that **identify which process** the entry belongs to.

**Benefits:**
- Allows TLB to hold entries from **multiple processes simultaneously**
- No need to **flush the entire TLB** on context switch (huge performance win)
- Provides **protection** — ensures a process can only use its own translations

> Without ASIDs, the TLB must be completely flushed every context switch (every entry becomes invalid), which is expensive.

### Hit Ratio and Effective Access Time (EAT)

**Hit Ratio** = percentage of times the page number is found in the TLB.

**Formula:**
```
EAT = (hit_ratio × memory_access_time) + ((1 − hit_ratio) × 2 × memory_access_time)
```

#### Example 1: 80% Hit Ratio

> Memory access time = 10 ns
>
> EAT = 0.80 × 10 + 0.20 × 20
>     = 8 + 4
>     = **12 ns**
>
> Slowdown = (12 − 10) / 10 = **20% slower**

**Breakdown:** 80% of the time we get lucky (TLB hit, 10 ns). 20% of the time we miss (need 2 accesses = 20 ns). Weighted average = 12 ns.

#### Example 2: 99% Hit Ratio (Realistic)

> EAT = 0.99 × 10 + 0.01 × 20
>     = 9.9 + 0.2
>     = **10.1 ns**
>
> Slowdown = only **1%**

**Takeaway:** A high TLB hit ratio (99%+) makes paging nearly free in terms of performance overhead.

## 12. Protection in Paging

### Valid–Invalid Bit

**Formal Definition:** Each page-table entry contains a **valid–invalid bit**:
- **1 (valid):** The page is in the process's logical address space and is legitimate to access
- **0 (invalid):** The page is NOT part of the process's address space

If a process tries to access a page marked invalid → CPU raises a **trap/exception** → OS handles it (may terminate the process).

### Protection Bits

Control **access permissions** per page:
- **Read (R):** Can the page be read?
- **Write (W):** Can the page be written to?
- **Execute (X):** Can the page's contents be executed as code?

The OS sets these bits to enforce memory protection between processes.

### Your Questions Answered

> *"Why hold pages 6 and 7 when they can't be accessed?"*

Pages 6 and 7 **don't actually hold process data** — they exist as **entries in the page table** because the page table must have a fixed structure. With a 14-bit address space (2^14 = 16,384 bytes) and 2 KB pages, there are exactly 8 page-table entries (pages 0–7). The OS marks pages 6 and 7 as **invalid** so any access to them causes a trap. They're not "held" in memory — they're just **marked as off-limits** in the table.

> *"Who changes the valid bit value?"*

The **Operating System** sets and changes the valid–invalid bit. When a process is created, the OS examines its size and marks only the pages that contain actual program content as valid. The rest are marked invalid. The hardware (MMU) **reads** this bit on every access to enforce the restriction, but only the **OS writes/changes** it.

### Textbook Example: Internal Fragmentation from Valid Bit

> 14-bit address space (0–16,383), page size = 2 KB, program uses addresses 0–10,468
> Pages 0–5 are valid (cover addresses 0–12,287)
> Pages 6–7 are invalid (addresses 12,288–16,383)
>
> **Problem:** Program only goes to 10,468, but page 5 covers 10,240–12,287.
> Addresses 10,469–12,287 are technically accessible (page 5 is valid!) even though the program shouldn't use them.
> This is **internal fragmentation** — the granularity of pages can't perfectly match the program's actual size.

## 13. Shared Pages

**Formal Definition:** Paging allows multiple processes to **share common code** by mapping their page-table entries to the **same physical frames**.

### Reentrant Code (Sharable Code)

**Formal Definition:** Reentrant code (also called **pure code**) can be safely executed by multiple processes simultaneously without interference.

**How it works:**
- Uses only **local variables** or **arguments** (no globals/shared mutable state)
- Each process has its **own copy of registers and data** (private data pages)
- The **code pages are shared**; the **data pages are private**

> **Interchangeable terms:** "Reentrant code" = "pure code" = "safely shareable code"

### Textbook Example: libc

> - `libc` (standard C library) = 2 MB
> - 40 user processes each need `libc`
> - **Without sharing:** 40 × 2 MB = **80 MB**
> - **With sharing:** 1 × 2 MB = **2 MB** (one physical copy, 40 page tables point to it)
> - **Savings: 78 MB!**

Other shareable programs: compilers, window systems, database systems.

## 14. Structure of the Page Table

The page table itself can become **huge**. Three main approaches to manage it:

### 14.1 Hierarchical Paging (Multi-Level Page Tables)

**Problem:** A 32-bit address space with 4 KB pages → 2^20 entries → **4 MB per process** just for the page table!

**Solution:** Page the page table itself — break it into smaller pieces.

#### Two-Level Paging (32-bit Example)

The 20-bit page number is split further:

```
| p1 (10 bits) | p2 (10 bits) | d (12 bits) |
| outer page   | inner page   | offset       |
```

- **p1** indexes into the **outer page table** → finds which page of the inner page table to use
- **p2** indexes into that **inner page table page** → finds the actual frame number
- **d** is the offset within the frame

> **Interchangeable terms:** "Two-level paging" = "forward-mapped page table" (because translation works from outer → inward)

**Advantage:** Only the outer page table must be in memory. Inner page table pages can be loaded on demand.

#### Why Hierarchical Paging Fails for 64-bit

Calculation chain for 64-bit, 4 KB pages:

> Page table entries = 2^64 / 2^12 = **2^52 entries**
>
> Two-level: inner tables = 2^10 entries each → outer table = 2^42 entries = **2^44 bytes (16 TB!)** — still too big
>
> Three-level: page the outer table into 2^10-entry pages → remaining outer = 2^32 entries = **2^34 bytes (16 GB)** — still enormous
>
> Four-level, five-level... 64-bit UltraSPARC would need **7 levels** → 7 memory accesses per translation → prohibitively slow

**Conclusion:** For 64-bit systems, hierarchical page tables alone are **inappropriate**.

### 14.2 Hashed Page Tables

**Formal Definition:** Uses a **hash function** on the virtual page number to index into a hash table. Each hash table entry contains a **linked list** (to handle collisions) where each element has:
1. Virtual page number
2. Mapped frame number
3. Pointer to next element

**How it works:**
1. Virtual page number is **hashed**
2. Go to that hash table bucket
3. Walk the linked list, comparing virtual page numbers
4. On match → use the stored frame number
5. Combine frame number with offset → physical address

**Variation — Clustered Page Tables:**
- Each hash table entry maps **several pages** (e.g., 16) instead of one
- Useful for **sparse address spaces** (where memory references are scattered)
- Good for **64-bit** systems

### 14.3 Inverted Page Tables

**Formal Definition:** Instead of one page table per process, there is **one system-wide page table** with one entry per **physical frame**. Each entry stores:
- The **virtual page number** stored in that frame
- The **process ID (PID)** of the owning process

**Address format (IBM RT):** `<process-id, page-number, offset>`

**Lookup:** Search the inverted table for a matching `<process-id, page-number>`. If found at entry `i`, the physical address is `<i, offset>`.

| Traditional Page Table | Inverted Page Table |
|---|---|
| One per process | One for entire system |
| Indexed by virtual page number | Indexed by physical frame number |
| Size proportional to virtual address space | Size proportional to physical memory |
| Fast lookup (direct index) | Slow lookup (must search) |
| Easy sharing (multiple entries → same frame) | Hard sharing (one entry per frame) |

**Problem:** Lookups are by virtual address, but table is sorted by physical address → **linear search** needed.

**Solution:** Use a **hash table** on top to speed up searches (limits search to a few entries).

**Sharing Problem:** Since there's only one entry per physical frame, a shared frame can only store **one** virtual mapping at a time. Other processes accessing the shared page cause a **page fault** and must replace the mapping — this is a fundamental limitation.

> Even with inverted page tables, the **TLB is checked first** before consulting the hash table, providing a performance boost.

## 16. Descriptive Mapping of All Concepts

### The Big Picture: How Everything Connects

```
PROGRAM (Logical/Virtual Side)                PHYSICAL RAM (Physical Side)
┌────────────────────┐                        ┌────────────────────┐
│  Page 0             │──── Page Table ────►  │  Frame 3           │
│  Page 1             │──── Entry     ────►  │  Frame 7           │
│  Page 2             │──── Entry     ────►  │  Frame 0           │
│  Page 3             │──── Entry     ────►  │  Frame 12          │
│  Page 4 (partial)   │──── Entry     ────►  │  Frame 21 (waste!) │
└────────────────────┘                        └────────────────────┘
   Contiguous                                    Scattered (non-contiguous)
   (programmer sees this)                        (OS manages this)
```

### Step-by-Step: A Memory Access

```
CPU generates logical address: 0x00005A3C
         │
         ▼
┌─────────────────────┐
│ Split into p and d   │ ◄── Power-of-2 page size makes this a simple bit split
│ p = 0x00005 (page 5)│
│ d = 0xA3C (offset)  │
└────────┬────────────┘
         │
         ▼
┌─────────────────────┐
│ Check TLB for page 5│
│                     │
│  HIT? ──► Frame 17  │──► Physical Addr = Frame17_base + 0xA3C ──► Access RAM
│                     │
│  MISS? ──► Go to    │
│    page table in RAM│──► Find frame 17 ──► Store in TLB ──► Physical Addr
└─────────────────────┘
```

### Example Walkthrough: Process Creation to Memory Access

**Scenario:** Process P has 5 pages. RAM has frames 0–31. Frames 2, 5, 9, 14, 27 are free.

1. **Process arrives:** OS sees P needs 5 pages
2. **Frame allocation:** OS allocates frames 2, 5, 9, 14, 27 to P
3. **Page table built:**

   | Page # | Frame # | Valid Bit |
   |--------|---------|-----------|
   | 0      | 2       | 1         |
   | 1      | 5       | 1         |
   | 2      | 9       | 1         |
   | 3      | 14      | 1         |
   | 4      | 27      | 1         |

4. **Frame table updated:** Entries 2, 5, 9, 14, 27 now marked "allocated to Process P"
5. **PCB updated:** Pointer to P's page table stored in PCB
6. **P gets CPU:** Dispatcher loads page-table pointer into hardware register
7. **P accesses address in page 2, offset 100:**
   - TLB checked → miss (first access)
   - Page table consulted → page 2 → frame 9
   - TLB updated with (page 2 → frame 9)
   - Physical address = frame 9 base + 100 → data retrieved
8. **P accesses page 2 again:**
   - TLB checked → **hit!** → frame 9 → fast access (no extra memory read)

### Hierarchical Paging: Two-Level Lookup

```
Logical Address (32-bit): 0xABC12345

Split: p1 = 0xABC >> 10 bits | p2 = next 10 bits | d = 0x345 (12 bits)

Step 1: Outer Page Table[p1] ──► points to Inner Page Table #X
Step 2: Inner Page Table #X[p2] ──► Frame number F
Step 3: Physical Address = F | d
```

### Summary Table: Page Table Structures

| Structure | Best For | Entries | Lookup Speed | Memory Cost |
|-----------|----------|---------|-------------|-------------|
| **Single-level** | Small address spaces | 1 per virtual page | O(1) direct index | High for large spaces |
| **Hierarchical** | 32-bit systems | Multi-level split | O(levels) | Moderate (sparse-friendly) |
| **Hashed** | 64-bit systems | Hash buckets + chains | O(1) average | Moderate |
| **Inverted** | Large physical memory | 1 per physical frame | O(n) worst, O(1) with hash | Low (one system-wide table) |
